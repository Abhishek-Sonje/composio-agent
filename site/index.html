Evidence-backed integration research, 2026

100 apps. One research agent.
What can actually become an agent tool today?

I built a research system to evaluate authentication, developer access, API surface, MCP support, and integration feasibility. Then I measured where it failed, rejected an optimization that made coverage worse, and kept the safety fixes.

Evidence coverage

The bottleneck wasn’t API discovery. It was proving developer access.

Authentication and API availability were usually discoverable, but credential/access requirements were often unclear. Because buildability requires supported auth + access + API evidence, many final verdicts remained unresolved rather than guessed.

A conservative agent by design

Each application runs independently through a bounded research and validation loop.

  1. App target
  2. Research controller
  3. Composio search + URL fetch
  4. Gemini synthesis
  5. Evidence ledger
  6. Deterministic sanitizer
  7. Structured JSON
supported claim → may survive unsupported claim → unknown

The agent prioritizes current official sources, researches one app at a time, and works within a ten-action budget. Search snippets discover sources; fetched pages support claims.

Structured output is locally validated, evidence is mapped to controlled field identifiers, and the 100-app runner resumes from valid result files after provider interruptions.

Precision and coverage are different product metrics

PrecisionWhen a supported claim survives, how often is it correct?

Coverage missWhen useful evidence exists, how often did the system still return unknown?

  1. Phase 1 validation37 correct · 0 incorrect · 0 unsupported

    The evidence ledger and sanitizer established a high-precision baseline.

  2. Production run100 / 100 completed

    Sequential, resumable execution survived quota interruption without losing work.

  3. Independent 14-app audit93.55% precision · 24.47% coverage miss

    Precision was strong; access and buildability coverage were the main weakness.

  4. Coverage experiment96.15% precision · 35.42% coverage miss

    Stricter control improved precision but made the product less complete.

  5. Final audit56 correct · 0 incorrect · 0 unsupported

    100% precision on surviving sampled claims; 28.57% coverage miss.

An optimization I rejected

The Phase 3B controller tried to allocate the budget more aggressively and recover more fields. It removed incorrect claims, but coverage miss rose from 24.47% to 35.42%. I restored the better research controller and retained only independently justified semantic safeguards.

Verification changed the system

Four failures found by the audit, and the rule each one produced.

Slack: HTTP is not REST

Keyword mapping called its Web API REST. Slack explicitly describes it as RPC-style, so REST now requires explicit official semantic support.

NotebookLM: source purity

Reverse-engineered cookie authentication polluted official Enterprise auth, so authentication methods now require matching official evidence.

Zendesk + NotebookLM: negative MCP

Client docs and third-party tooling implied product absence, so negative MCP claims now require explicit official evidence.

Salesforce: mapping loss

Good evidence existed but nested fields were dropped, so the controlled evidence ledger now preserves exact field support.
